# Чаты через GREEN-API

Веб-интерфейс для отправки и получения текстовых сообщений через
[GREEN-API](https://green-api.com). Работает с инстансами **MAX**,
**WhatsApp** и **Telegram** — мессенджер определяется инстансом, отдельного
переключателя в приложении нет.

Стек: React 19 + TypeScript + Vite, сборка и деплой — Vercel.

## Возможности

- Подключение к инстансу GREEN-API по `idInstance` и `apiTokenInstance`
- Проверка инстанса через `GetStateInstance` перед входом
- Список реальных чатов с поиском и счётчиками непрочитанных
- Создание чата по номеру телефона: `CheckAccount` возвращает `chatId`
- Отправка текста через `SendMessage` со статусами доставки
- Приём входящих сообщений опросом очереди `ReceiveNotification`
- Тёмная тема и адаптивная вёрстка: на мобильных список чатов уезжает вбок

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # tsc -b && vite build
npm run preview
npm run lint
npm run format
```

## Переменные окружения

Обязательных переменных нет: пользователь вводит учётные данные инстанса
в интерфейсе, они сохраняются в `localStorage` браузера.
`.env.example` — заготовка на случай, если понадобится инстанс по умолчанию.

## Как устроена интеграция

Браузер не ходит в GREEN-API напрямую. Все запросы идут через serverless-функцию
`api/green-api.ts` (Vercel), потому что:

1. GREEN-API не отдаёт CORS-заголовки для cross-origin вызовов из браузера.
2. `apiTokenInstance` входит в путь URL GREEN-API — напрямую из клиента он
   осел бы в истории браузера и в devtools.

Клиент шлёт `POST /api/green-api` с заголовками `x-green-id-instance`,
`x-green-token` и телом `{ method, payload }`. Функция держит белый список
методов, собирает URL GREEN-API и проксирует ответ как есть.

Обработчик лежит в `server/greenApiProxy.ts`. Его используют обе точки входа:
`api/green-api.ts` — serverless-функция на Vercel, и dev-сервер Vite
(плагин `greenApiDevProxy` в `vite.config.ts`). Поэтому `npm run dev` тоже
работает: Vite монтирует тот же обработчик на `/api/green-api`.
Без этого плагина подключение инстанса падало бы с 404 — serverless-функции
выполняет только Vercel, обычный Vite про `/api` ничего не знает.

| Задача               | Метод GREEN-API                              | HTTP    |
| -------------------- | -------------------------------------------- | ------- |
| Проверка инстанса    | `GetStateInstance`                           | GET     |
| Список чатов         | `GetChats`                                   | GET     |
| Поиск чата по номеру | `CheckAccount`                               | POST    |
| Загрузка переписки   | `GetChatHistory`                             | POST    |
| Отправка текста      | `SendMessage`                                | POST    |
| Входящие уведомления | `ReceiveNotification` + `DeleteNotification` | GET/DEL |

У метода `CheckAccount` есть квота: тариф Developer разрешает 100 проверок
номеров в сутки. Поэтому найденный `chatId` кэшируется в `localStorage`
вместе со списком чатов, и повторно один и тот же номер не проверяется.

`GetChats` отдаёт `id`, `name`, `type`, `unreadCount` и `archive`, но не
последнее сообщение и не аватар. Поэтому превью приложение держит локально
и дополняет им список из хранилища.

Тело запросов проверяется строго: лишний ключ даёт
`Validation failed. Details: '<поле>' is not allowed`. Идентификатор чата
передаётся только как `chatId`, даже если в ответе `GetChats` он лежит
в поле `id`.

Для приёма сообщений в настройках инстанса `webhookUrl` должен быть пустым,
а `incomingWebhook` / `outgoingWebhook` / `stateWebhook` — включены
(настраивается в личном кабинете или через `SetSettings`).

## Различия между мессенджерами

Приложение само ничего не различает: набор методов, полей ответов и
состояний у MAX, WhatsApp и Telegram совпадает, а канал задаёт инстанс.
Код учитывает только то, что реально расходится:

|                             | MAX                     | WhatsApp          | Telegram          |
| --------------------------- | ----------------------- | ----------------- | ----------------- |
| Идентификатор в `GetChats`  | поле `id`               | `id` или `chatId` | `id` или `chatId` |
| Формат идентификатора       | JID `…@g.us` / `…@c.us` | JID `…@c.us`      | число             |
| Имя в поле `chatId` запроса | да                      | да                | да                |

Номер телефона извлекается из идентификатора, только если там 11–12 цифр
подряд: у групп локальная часть JID — это `номер-меткаСоздания`, то есть
телефон там не номер чата. Номера без такой структуры (Telegram) берутся
из поля `phoneNumber`, если API его отдаёт.

Требование «собеседник должен сохранить ваш номер в контактах» действует
для MAX и WhatsApp. У Telegram такого ограничения нет.

## Деплой на Vercel

```bash
npx vercel
```

`vercel.json` содержит rewrite для SPA, чтобы `/chat/:id` переживал перезагрузку
страницы. Функция `api/green-api.ts` задеплоится как serverless-функция.

## Ограничения

- Токен хранится в `localStorage`, то есть доступен скриптам на этой странице.
  Для продакшена нужны serverless-сессии или бэкенд.
- `idInstance` и `apiTokenInstance` передаются в serverless-функцию из браузера
  пользователя. Это токен самого пользователя, секретов приложения в репозитории нет.
- Переписка и превью чатов кэшируются в `localStorage`: `GetChatHistory` не
  отдаёт историю целиком, а `GetChats` — последние сообщения.
- Работают только текстовые сообщения. Картинки, файлы, голосовые, опросы и
  реакции из очереди `ReceiveNotification` отбрасываются.
- Отправить сообщение в MAX или WhatsApp можно только тем номерам, которые
  сохранили номер вашего аккаунта в своих контактах.
